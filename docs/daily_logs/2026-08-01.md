## 4. 🚨 重大バグ発見・修正: BrokerClient.fetch_latest_quote() が誤ったAlpacaホストを叩き、07-29 18:44 JST以降全BUYが停止していた

### 発見の経緯

オプション3（collect_data.pyのbrokerソース収集実装）の事前検証中に、`BrokerClient.fetch_latest_quote()` が常に404を返していることを発見。

### 根本原因

```python
def fetch_latest_quote(self, symbol):
    return self.fetch(endpoint=f"v2/stocks/{symbol}/quotes/latest")
```

`self.fetch()` は `self.base_url`（= `paper-api.alpaca.markets`、取引アカウントAPI）にリクエストするが、Alpacaの相場データは別ドメイン `data.alpaca.markets` にしか存在しない。同じファイル内の `fetch_bars()` は正しく `data.alpaca.markets` をハードコードしていたが、`fetch_latest_quote()` だけこの修正が漏れていた。

### 影響連鎖（重要）

1. `paper_demo.py` の `get_mid_price()` はこの `fetch_latest_quote()` を呼び、例外を全て捕獲して `price=0.0` を返す
2. `c948f57`（07-29 18:44 JST, FIX-002）で、allocation段階の `get_mid_price() <= 0` 判定を「$100フォールバック」から「即時BUYブロック」に変更（意図は正しい修正だった）
3. 両者が重なり、**07-29 18:44 JST以降の全新規BUYが一件例外なくサイレントに停止**していた（ログは `SKIP BUY <symbol>: allocation price unavailable` のみ）
4. **これはMEMORY.mdに記録済みの2件のバグ（STOCK_MULTIPLIER二重計上、broker.get_account()タイプミス）とは別の、3件目のBUY停止バグ**。先の2件を修正しても、このバグが残っていたためBUYは復旧していなかった

### 検証（data/tracking/pnl_state.json）

entry_time >= 2026-07-29T09:44:10 UTC（fixデプロイ時刻）で、`reconciled_from_broker` を除く本物の新規BUYは **0件**。

### 修正内容

- `BrokerClient._fetch_market_data_endpoint()` を新設（`fetch_bars()` の既存実装から共通化）
- `fetch_latest_quote()` をこのヘルパー経由で `data.alpaca.markets` を叫ぶように変更
- `fetch_bars()` も同じヘルパー経由にリファクタ（動作不変、既存+新規テストで確認）

### 実机検証

本番 paper アカウントに対し実際にAPI呼び出しを実施。DDOG/NVDA/AMD/HPEはHTTP 200で実際のbid/askを取得確認（修正前は全銘柄で404）。MSFTのみap=0のスナップショットがあったが、これはIEX無料フィードの取引時間外流動性特性（bpは正常に取得できていた）で、ルーティングバグとは無関係と確認。

## 5. 🚨 重大バグ発見・修正: decisionファイルの命名衝突による大規模データ喪失（プロジェクト開始以来の構造的バグ）

### 発見の経緯

07-31 MSFT BUY調査の延長で、他にもdecisionファイルの損失がないか全期間の監査ログを走査したところ、**プロジェクト開始（04月）以来スーっと存在していた別の重大バグ**を発見。

### 根本原因

`_save_decisions()`（paper_demo.py）が decision ファイルを `decision_{symbol}_{ts_tag}.json` という、**run単位でしか変わらないファイル名**で保存していた。同一run内で同じ銘柄に対し複数の決定（例：新規BUYシグナル + 既保BUYポジションのSELLシグナル）が発生すると、後から書かれた方が前の内容を**無条件で上書き**してしまう。

### 影響範囲

全期間（04月〜07月）の監査ログを走査した結果、**700件以上の同一銘柄・同一run衝突グループ**を検出。上書きされた決定のevidence/sizing/confidenceは完全に失われており、監査ログの1行だけが証拠として残っている。

### 修正内容

- ファイル名に `decision_id`（全決定中一意）を付加: `decision_{symbol}_{ts_tag}_{decision_id}.json`
- 同様の脆弱性があった `analyze_data.py` の `create_decisions()` も同様修正
- 全読み取り側（console/services/*.py, scripts/*.py等）はglobワイルドカードパターン使用であることを全件確認済み（後方互換）

### テスト

- `test_same_symbol_same_run_decisions_do_not_overwrite_each_other`: buy+sell同時保存を検証。修正revertで本番同様症状で失敗することを確認mutation-killerとして機能
- フルテストスイート: 1272 passed, 2 skipped（+1件、リグレッションなし）

commit `90ab2b0`、push済み。

**重要**: 過去の700件以上の上書き消失データは復元不可能（ディスクに一度も正しく保存されていないため）。今後の喪失は防止される。
