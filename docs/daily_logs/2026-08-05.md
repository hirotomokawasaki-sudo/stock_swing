## 1. Stop Loss: tiered min_hold v2（offset_pct 再設計・再有効化）

### 背景

ユーザーから「7月の改修効果」「今後の改善計画」「システムの安定性・パフォーマンス評価」
「Exit戦略（Trailing/Breakeven/Stop Loss）の言語化」「その改善案」について順に質疑があり、
最後にStop Loss戦略の改善案として提案した「tiered min_hold の再有効化」に着手した。

### 問題

- 2026-07-27 Plan A（commit `52736ca`）で tiered min_hold を導入。post-exit drift 分析
  （48件）で「損失幅の浅いstop_lossはノイズで回復しやすく、深いものは回復しない」ことが
  判明し、損失幅に応じてmin_hold（最低保有日数）を段階化する設計だった。
- しかし tier 判定が **絶対値の return_pct**（例: 「return > -5% → 7日」）で実装されており、
  2026-07-29 FIX-007（commit `687c5c5`）で無効化された。
- 無効化の理由: standard(-7%)/high-conviction(-9%) の stop_loss は、その閾値に到達した時点で
  既に return ≤ -7%/-9% であり、「-5%より大きい」ことを構造的に満たせない。7日tierが
  事実上デッドコードになっていたのは low-conviction(-5%)銘柄以外全て、というのが実態。

### 修正内容

tier 判定を絶対値ベースから、**発火した有効stop閾値からの相対オフセット（offset_pct、
percentage point単位）**ベースに再設計した。

```
offset_pct = (return_pct - eff_stop_loss_pct) * 100
```

これにより conviction tier（-5%/-7%/-9%）に関わらず、閾値をわずかに超えた直後は常に
offset_pct ≈ 0（ノイズ域）、深く超えるほど offset_pct が大きくマイナス（真の止損域）になり、
全ての conviction tier で7日tierが到達可能になった。

**実装変更**:
- `src/stock_swing/strategy_engine/simple_exit_v2_strategy.py`
  - `_effective_min_hold_days()` に `eff_stop_loss_pct` 引数を追加し、offset_pct を計算
  - `tiered_min_hold_levels` の schema を `threshold_pct` → `offset_pct` に変更
  - stop_loss 判定ブロックの呼び出し箇所を更新
- `config/strategy/simple_exit_v2.yaml`
  - `tiered_min_hold_enabled: false` → **`true`**
  - `tiered_min_hold_levels` を offset_pct ベースに書き換え（-2.0pp→7日 / -5.0pp→3日 / それ以上→base 1日）
  - `tiered_min_hold_disable_reason` 削除
- `src/stock_swing/reporting/console_renderer.py`: 表示ラベルを offset_pct 表記に更新

### テスト

- `tests/unit/test_simple_exit_v2_strategy.py`: Plan A テスト群（14件）を offset_pct ベースに
  全面書き換え。境界値のfloat誤差を避けるため境界からずらした値を使用。
  low-conviction/high-conviction 到達性の回帰テストを2件追加。
- `tests/unit/test_fix007_yaml_disable.py`: 「無効化されていること」の検証から「offset_pct
  ベースで再有効化されていること・全conviction tierで到達可能であること」の検証に更新。
- フルテストスイート: **1325 passed, 2 skipped**（既存の無関係な2件の失敗のみ、07-30以前から
  記録済みの既知issue）

### ロールバック

`config/strategy/simple_exit_v2.yaml` の `tiered_min_hold_enabled: false` に戻すだけで
即座に旧動作（一律 min_hold_days=1）に戻る。

### 今後の確認事項

- 07-27時点のシミュレーション根拠（-$167K→-$126K、+$41K改善）は絶対値ベースのバックテストに

## 3. Sector Shock A/B: Historical Replayデータ蓄積開始

### 背景

Stop LossのSector Shock閾値見直し（A/B開始）の前提条件として、R3-v2のActivation
criteriaの一つである「historical shock replay ≥100 events」の達成に向け、
過去データの遡及的な再分類を開始した。

### 実施内容

- `scripts/sector_shock_historical_replay.py` 新規作成
- 過去のloss-mitigation exit（stop_loss + breakeven_stop、計111件、2026-05-14〜07-30）
  のexit日について、当日の実際のセクターベンチマークリターン（data/benchmarks/
  benchmark_returns.csv）+ シンボル自体のexit日リターン（yfinance）を使い、
  `SectorShockAnalyzer.classify()`で「もし当時有効だったらどう分類されていたか」を再現
- Read-only（過去のexit判断を変更しない、再分類のみ）
- 出力: `data/sector_shock_historical_replay_log.jsonl`（shadow logとは別ファイル）

### バグ修正

当初実装ではシンボルのreturn取得キャッシュが「entryの初回呼び出し時の日付範囲」だけで
固定され、同一シンボルが別日付で再登場した場合にNo dataになる不具合を発見。
全トレードのexit日を事前に集計してシンボルごとに広い日付範囲で一括取得する方式
（`_prefetch_all_symbol_prices`）に修正し、全111件を欠損なく再分類できるようにした。

### 結果

- **historical shock replay: 111件（目標100件を達成）**
- 分類内訳: soft_stop 82件、recovery_hold_timeout 28件、relative_weakness_exit 1件
- **有効な sector-shock context（sector_shock_hold + relative_weakness_exit）は
  わずか1件**（TSM 2026-07-01）

### 結論（重要）

historical replay件数の目標は達成したが、「有効なショック事例」の蓄積は依然として
不足している。実際のセクター全体ショック（現行閾値-3.0%超え）自体が監査期間中に
ほとんど発生していないことが根本原因であり、閾値見直し（例: -3.0%→-2.0%）の
検討はこのデータを基に行う必要がある。forward valid stop-trigger shadow（目標
10件）も現在0件（現行shadow log 17件全てsoft_stop）のまま。

### 今後の確認事項

- 閾値見直しの具体案を次回検討（例: -3.0% → -2.0% での再シミュレーション）
- forward shadow（paper_demo実行中のリアルタイム分類）は引き続き自然蓄積を待つ方針

## 4. Sector Shock 閾値見直し（-3.0% → -2.0%）検証 → 変更見送り

### 検証内容

historical replayデータ（`data/benchmarks/benchmark_returns.csv`、61営業日分）を使い、
現行閾値-3.0%と見直し案-2.0%/-2.5%/-1.5%/-1.0%それぞれで、セクターショック検知日数を
再集計した。

### 結果

| 閾値 | 検知日数 |
|---|---|
| -3.0%（現行） | 9日 |
| -2.5%（中間案） | 14日 |
| -2.0%（見直し案） | 14日 |
| -1.5% | 16日 |
| -1.0% | 22日 |

-2.0%への引き下げで新たに検知される7件（AVGO, CHPS, FTXL, INTC, SHOC, SMCI, SOXX、
いずれも05-15/06-10/07-02/07-07発生）についてrelative_weakness_ratioを再計算した結果:

- **hold候補になるのは3件のみ**（AVGO ratio=1.26, SHOC ratio=1.53, SOXX ratio=1.54）
- 残り4件（CHPS, FTXL, INTC, SMCI）はratio>2.0でrelative_weakness_exit判定となり、
  結局現行同様exitする

### 判断: 閾値変更は見送り（ユーザー判断、2026-08-05）

**理由**:
1. 効果が限定的（61営業日でhold候補+3件のみ）
2. 誤判定（本来exitすべき局面を誤ってhold）のリスクとのトレードオフが五分五分
3. サンプル数が少なすぎて、hold候補3件が実際に「holdが正解だったか」を検証する
   post-exit driftデータがまだない
4. 「A/B開始条件（件数）を満たすために閾値を動かす」のは本末転倒になりかねない
   （本来は自然なショック発生を待つ設計方針）
5. hard_loss_cap_pct=-15%が独立して効くため、SMCIのような極端なケース
   （symbol_1d -28%）は閾値変更に関わらずそもそもholdされない安全弁は存在する

### 結論

**SECTOR_SHOCK_THRESHOLD_PCT は現行 -3.0% を維持する。** 引き続き自然なショック
発生によるforward shadow蓄積を待つ方針を継続。historical replayログ
（`data/sector_shock_historical_replay_log.jsonl`、111件）は今後の判断材料として
保持する。

## 6. Small-Sample Watchlist（entry filterの可視化拡張）

### 問題

stock_reduced gate（min_n=5）は、n=2〜4の小サンプルですでに大幅赤字の銘柄
（IBM n=3 pnl=-$8,513 WR=0%、ORCL n=3 pnl=-$8,306 WR=33%、PLTR n=2 pnl=-$6,712 WR=0%、
CDNS n=2 pnl=-$5,940 WR=0%等）を検知できず、放置していた。

### 方針判断

min_nを単純に下げると小サンプルでの誤判定（統計的に不十分な根拠でのブロック）
リスクが上がるため、**自動ブロックの拡大ではなく可視化の追加**という保守的な
アプローチを採用。

### 実装

- `src/stock_swing/risk/entry_filter.py`:
  - `SymbolPFStats`に`win_rate`フィールド追加
  - `get_small_sample_watchlist()`新規関数（n=2〜4かつnet_pnl<0の非ETF銘柄を抽出、
    read-only・何もブロックしない）
- `paper_demo.py`: run毎に計算して`entry_filter_stats`に格納
- `console_summary.py` / `console_renderer.py`: BUY STOP LISTの下に
  「⚠️ SMALL-SAMPLE WATCHLIST」として表示
- テスト: `test_entry_filter.py`に8件新規追加

### 検証

実データで実行確認: IBM, ORCL, PLTR, CDNS含む19銘柄がwatchlistに表示されることを確認。
