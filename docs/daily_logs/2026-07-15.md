# 2026-07-15 実装ログ — order_rejection_rate_pct 閾値緩和

## 背景

2026-07-14 のログに「調査ポイント」として挙げられていた `order_rejection_rate_pct` ルールの閾値見直しを実施。

**問題の構造**
- 現行閾値 10% は少数 submission 時に過敏すぎる
- FRWD 0-qty SELL 1件 / 8件送信 = 12.5% → `block_buys` 誤発動（07-14 HALT の間接要因）
- 0-qty SELL 自体は 07-14 の SELL guard（commit a6938d7）で既に除外済みだが、閾値は未修正のまま残存

**設計判断**
- `broker_tracker_mismatch_count >= 1` が既に HALT をトリガーするため、`rejection_rate` は補助的な指標
- `block_buys` アクションは HALT より緩やかだが、10% は正常な市場条件でも超過しうる
- 最低 4件以上の submission がある場合のみ rate を評価する（小サンプル誤発動防止）

---

## 変更内容

### 1. YAML 閾値変更（`config/guardrails/autonomous_stop.yaml`）

| 項目 | 変更前 | 変更後 |
|------|--------|--------|
| `order_rejection_rate_pct` threshold | 10.0% | **25.0%** |

**根拠**
- 25% = 4件送信で 1件却下まで許容（通常の market condition で現実的な上限）
- SELL guard 実装後は 0-qty SELL 起因の誤却下が除去済みのため、残る却下は真の API/broker エラー
- api_error_rate_pct（20%）と揃えた水準

### 2. 最小件数ガード追加（`src/stock_swing/cli/paper_demo.py`）

```python
# Before
len([rejected]) / max(len(submissions), 1) * 100

# After
len([rejected]) / len(submissions) * 100 if len(submissions) >= 4 else 0.0
```

- `submissions < 4` の場合は rate = 0.0（rule をスキップ）
- 少数サンプル（1〜3件）で 1 rejection が 33〜100% になる誤発動を防止
