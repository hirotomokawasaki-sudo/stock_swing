## ブローカー移行計画（Alpaca → IBKR）策定

**背景**: 業務都合により本番ブローカーを Alpaca から Interactive Brokers (IBKR) に
移行する必要がある（マスト、是非の議論対象外）。9/15 のリアルトレード Go/No-Go
判定（R0-R9 ロードマップ、戦略パフォーマンス評価）とは完全に独立したトラックとして扱う
ことをユーザーと確認。

**ユーザー確定事項**:
- 移行順序: Alpaca Paper → IBKR Paper → IBKR Live（提案どおり妥当と回答）
- 2環境運用（IBKR Paper + IBKR Live）: 賛成。既存 `runtime_mode` 4段階設計・
  Plan B/C/D/E の shadow→paper_ab→active 昇格パターンと思想が一致
- IBKR 口座開設: 申請中、完了時期は会社都合のため未定
- 接続方式（TWS/IB Gateway vs Client Portal Web API）: 未定
- 移行開始日: 未定 → **D0（移行開始日）からの相対日程でスケジューリング**する方針で合意

**技術調査で判明した点**:
- `BrokerClient`（`src/stock_swing/sources/broker_client.py`）は Alpaca REST 専用実装
  （APCA-API-KEY-ID ヘッダ、paper-api.alpaca.markets / data.alpaca.markets 固定）
- `config/runtime/current_mode.yaml` にも「ALPACA_MODE must equal 'paper'」等 Alpaca 前提の
  記述あり
- 救い: `PaperExecutor` / `Reconciler` が broker_client に要求する I/F は
  fetch_account/fetch_positions/submit_order等の狭いダックタイピングのみ →
  Protocol化すれば IBKR実装への差し替えは設計上可能
- 過去のインシデント（Alpaca stale price, get_account()メソッド不存在によるBUY停止2日11時間、
  equity計算バグ等）は軒並み「ブローカーAPIの想定外挙動」が原因 → ブローカー切替はこの種の
  バグを最も誘発しやすいイベントであり、shadow運用期間を必ず挟む方針とした
- IBKR固有の差分: 接続方式（常駐Gateway要）、識別子（conId中心）、市場データ（有料サブスク要）、
  約定モデル（execId複数exec+commission report別建て）、Paper口座がLive口座に紐づく形で発行

**成果物**: `docs/broker_migration_ibkr_plan.md` を新規作成
- Track A（D0非依存、今すぐ着手可能）: Alpaca前提コード棚卸し、BrokerClientProtocol定義、
  environment_id対応設計、接続方式比較資料、日次運用負荷見積り
- Track B（D0依存）: 接続スパイク→IBKRBrokerClient実装→Alpaca Paperとのシャドー運用
  →IBKR Paper昇格判定→IBKR Live開設確認→段階サイズでLive稼働開始
- 評価指標分離: ブローカー統合健全性 と 戦略パフォーマンス(PF/WR) を混同しないよう
  environment_id付き台帳で隔離する方針
- 未決事項リスト（接続方式、口座開設時期、Live取引許可要否、Alpaca維持期間）を明記

**次のアクション**: Track A 着手可否をユーザーに確認待ち。D0確定後に相対日程を実カレンダーに変換。

## Track A（A1～A5）完了

ユーザーから「進めて」の指示を受け、Track A全項目を実施。commit `5783d7e`。

### A1: Alpaca前提コードの棚卸し
`docs/broker_migration_alpaca_assumptions_audit.md` 作成。ブローカー接続層・fill_ledger・
 reconciliation status mapping・symbol識別子(conId)の4点を「作り直し必須🔴」として特定。
 PaperExecutor/day_start_snapshot/hybrid_data_fetcherはI/Fが狭くすでに抽象化されており
 Protocol化後はほぼ無改修で動く見込み（🟢）と判定。

### A2: BrokerClientProtocol 定義（実コード変更）
`src/stock_swing/sources/broker_client_protocol.py` 新規作成（`@runtime_checkable
 Protocol`、fetch_account/fetch_positions/submit_order等の狭いI/Fを型として固定）。
 `PaperExecutor` / `Reconciler` / `LiveGuardedExecutor` / `ProductionExecutor` /
 `HybridDataFetcher` の型注釈を `BrokerClient`(Alpaca具体実装) →
 `BrokerClientProtocol` に変更（挙動変更なし、型ヒントのみ）。

**テスト**: `tests/unit/test_broker_client_protocol.py` 新規23件（Alpaca実装がProtocolを
 構造的に満たすこと、シグネチャ一致、非継承クラスでもconformすることを確認）。
 フルスイート実行: **1904 passed, 2 skipped**（既存の無関係スキップのみ、regressionなし）。

### A3: environment_id 対応設計（設計のみ、実装はTrack B）
`docs/broker_migration_environment_id_design.md` 作成。`pnl_state.json` /
 `fill_ledger.jsonl` / `day_start_snapshot.json` に `environment_id`
（alpaca_paper/ibkr_paper/ibkr_live）を導入する設計。目的はD0+3〜6週の
 Alpaca/IBKRシャドー運用期間中に両ブローカーのトレードが同一台帳で混在しPF/WR集計や
 ledger_quality_gate判定を汚染しないようにすること。既存の`get_summary_by_account`
 パターンを踏襲すれば集計側は小さい変更で済む見込み。

### A4: IBKR接続方式比較
`docs/broker_migration_ibkr_connection_method_comparison.md` 作成。TWS/IB Gateway
（`ib_insync`/`ib_async`） vs Client Portal Web APIを比較。暫定推奨はCPAPI（現行
 `BrokerClient`がすでにhttpxベースのHTTP+JSON方式であり移植の心理的障壁が低いため）。
 **重要**: web検索ツールが使えなかったため、本比較は一般知識ベースの一次資料。IBKR公式
 ドキュメントでの裏取りを接続方式決定前に必ず実施することを文書中に明記。

### A5: IB Gateway常駐運用の日次負荷見積り
`docs/broker_migration_ibkr_operational_load_estimate.md` 作成。Gateway常駐化・
2FA自動化の可否・Paper/Live 2プロセス運用の負荷を見積もり。**2FA自動化の成否が
 プロジェクト全体最大のリスク要因**と結論、Track B最初期（D0+1週の接続スパイク）で
 最優先検証すべき項目として位置づけ。

**次のアクション**: Track A完了。接続方式の最終決定（IBKR公式ドキュメントでの裏取り含む）と
 D0（移行開始日）確定を待つ。D0確定後にTrack Bの詳細スケジュールを確定日程に更新。

## 日本株 AI/半導体拡張ロードマップ 立ち上げ + Phase 1検証実施

**背景**: IBKR移行後は日本株も売買対象になることを受け、ユーザーから「現在の米国のAI・
テック・半導体と相性のよい対象や戦略はあるか」と発問。回答として日本の半導体製造装置・
材料・パッケージング銘柄群を提示したところ、「ロードマップ立ち上げて検証進めて」との指示。
ソフトバンクグループ（9984）はインサイダー該当で購入対象外（検証はOK）との指示も受領。
追って詳細の購入禁止リストも提供される予定。

**作成したもの**:
- `docs/jp_semiconductor_ai_expansion_plan.md`（新規）— IBKR移行計画（Track A/B）とは
  完全に別トラックのロードマップ。Phase 1（相関検証、IBKR接続不要）→ Phase 2（戦略設計）
  → Phase 3（実運用配線、IBKR接続必須）の3段階構成。購入禁止リスト（deny-list）のplaceholderも設け（現在
  9984のみ登録）
- `scripts/analyze_jp_semiconductor_correlation.py`（新規）— Yahoo Finance経由で米国半導体
  指数（SOXX/SMH/NVDA/QQQ）と日本候補銘柄（Tier1-3 + SoftBank参考）の同日相関・
  スピルオーバー相関（US(t) vs JP(t+1)）・条件付きギャップ分析を計算する取得専用のリサーチ
  ツール（pnl_stateには一切接続しない）
- `tests/unit/test_analyze_jp_semiconductor_correlation.py`（新規）— 合成データによる
  相関計算・ギャップ分析の単体テスト5件（全PASS）

**Phase 1検証結果（実データ、Yahoo Finance 2年分）**:
- 全候補銘柄で「同日相関（0.06〜0.18）よりスピルオーバー相関（US SOXX(t) vs JP(t+1)、
  0.37〜0.52）の方がはるかに強い」ことを確認 → オーバーナイト・スピルオーバー仮説を実データで支持
- Tier 1銘柄（Tokyo Electron 0.524 / Disco 0.476 / Advantest 0.470）がスピルオーバー
  相関上位3位を占め、事前の仕設（直接連動度が高いはず）を裏付け
- 条件付きギャップ分析: |SOXX日次リターン|≥2%の日の翻朝、Advantest/Tokyo ElectronはUP
  方向一致率90%、FujikuraはDOWN方向一致率95%と非常に高い。一方で平均ギャップ幅は
  約2〜3%と大きく、既に情報の大部分が寄り付き時点で反映済みと示唆
- 6967.T（新光電気工業）は2023年JIC Capitalによる非公開化（上場廃止）でYahoo取得不能を
  確認、候補から除外
- **判定: ✅ GO。Tier 1全銘柄が相関係数0.4以上・方向一致率60%以上の基準をクリア。Phase 2（戦略設計）へ**
