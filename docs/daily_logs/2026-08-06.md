### 🚨 緊急対応: console HTTP watchdog 無限再起動ループ（10:18〜11:20 JST、約1時間）

**発見の経緯**: 「現在対応が必要な問題は起きていますか」との質問を受け、cron/launchd/ログを
広く確認したところ、`logs/launchd_watchdog.log` が異常な頻度（約68秒おき）で HTTP console の
再起動を繰り返していることを発見（当該ログだけで2500件超の "unhealthy" 記録）。

**根本原因**:
- `console/app.py` の `/health` エンドポイントが `run_self_check()` を同期呼び出し
- `run_self_check()` → `_check_cron_run_history()` が有効な cron job 1件ごとに
  `openclaw cron runs --id ... ` をサブプロセスで実行（現在14ジョブ → 14回のサブプロセス起動）
  → 実測 **11.7秒**
- launchd watchdog（`console/manage.sh watchdog-run-once`）の `/health` probe は
  `curl --max-time 5`（5秒タイムアウト）
- 常に probe がタイムアウト → watchdog が unhealthy 判定 → HTTP console 再起動
  → 新プロセスも起動直後の初回リクエストで同じ11.7秒がかかる → 再び unhealthy → 無限ループ

**修正（commit `87d0080`）**:
- `run_self_check()` をバックグラウンドスレッドで30秒おきに定期実行し、結果をキャッシュする方式に変更
- `/health` はリクエスト内で `run_self_check()` を直接呼ばず、キャッシュされたスナップショットを
  読むだけ（初回未計算時は軽量な "not_yet_computed" プレースホルダを返す）
- これにより `/health` は常に非同期・高速応答（実測 0.016〜0.038秒）になり、watchdogのタイムアウトに
  引っかからなくなった

**検証**:
- 修正後、console restart → watchdog を4分以上連続監視し、healthy判定が継続することを確認
  （修正前は約68秒おきに再起動していた）
- `tests/unit/test_console_self_check_service.py`（5件）+ `console` 関連テスト全体（110件）が
  全て pass することを確認（テスト自体は `_check_cron_run_history` の実サブプロセス呼び出しを
  含むため実行に約1〜2分かかる — これは想定通りの重さで、今回の問題の原因そのものでもある）

**影響範囲**:
- HTTP console は1時間以上不安定な状態（起動直後にkillされる状態）が続いていたが、
  WebSocket server・paper_demo・reconcile_orders 等の取引系cronには影響なし
  （watchdogはHTTP consoleとWebSocketのみを監視・再起動する対象）
- ユーザーが直接コンソールUIを見ようとした場合、断続的に接続できない状態だった可能性がある

**今後の確認事項**:
- `_check_cron_run_history` 自体の遅さ（サブプロセス14回×直列実行）は温存されたまま。
  cron job数が今後さらに増えると悪化するため、`/api/console/self_check` エンドポイント
  （こちらは今回未修正、同期呼び出しのまま）で同様の遅延が起きうる。次回改善候補：
  - サブプロセス呼び出しの並列化、または `openclaw cron runs` のバッチAPI化
  - `_CRON_TIMEOUT_S`（現在10秒）の見直し
- watchdogの5秒タイムアウトが今回のように「常に間に合わない」設計だったこと自体も一因。
  今後同種のヘルスチェックを追加する際は、watchdog probe timeout と実処理時間の関係を
  必ず事前検証する

## 4. フォローアップ改善: 残っていた同期 run_self_check() 呼び出し3箇所をキャッシュ化

**背景**: 上記の `/health` 修正時点で、同じ `run_self_check()` を同期的に呼んでいる箇所が
コンソールAPIに他に3つ残っていることに気付いた（`/api/overview` / `/api/system_status` /
`/api/console/self_check`）。これらはブラウザでダッシュボードを開いた際に呼ばれる主要APIであり、
`/health`と同根の最大11.7秒ブロッキングが残っていた。

**修正（commit `024ef8d`）**:
- `/api/overview` と `/api/system_status`: レスポンスを30秒TTLでキャッシュ（`_compute_once`の
  single-flight方式）、evidence gateには`/health`と同じバックグラウンド更新スナップショットを使用
- `/api/console/self_check`: 同じバックグラウンドスナップショットをそのまま返すよう変更
  （個別に`run_self_check()`を呼ばない）

**検証**:
- console再起動後の初回呼び出し: `/api/overview` 14.15秒、`/api/system_status` 12.09秒
  （キャッシュ未形成時、想定通り）
- 2回目以降の呼び出し: 全て10ms未満（キャッシュヒット）
- `console` 関連テスト110件 全pass
- commit後の post-commit auto-restart 後も watchdog を3分以上監視し healthy 継続を確認

## 5. 次アクション項目の実施: _check_cron_run_history の並列化

**背景**: 4.の修正時点で残タスクとして記載した「サブプロセス直列実行の並列化」を同日中に実施。
