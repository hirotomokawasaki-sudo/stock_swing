## Stop Loss 再設計：目的の再定義と実データ検証（役割純化方針）

**背景**: ユーザーとの議論で、stop_lossの本来の目的を「単体で勝つ戦略ではなく、
数ヶ月以上の長期にわたって回復の見込みがないような急落から資産を守ること」と
再定義。この目的に照らして現行実装が妥当かを深掘り検証した。

### 検証結果（衝撃的だった発見）

1. **真の止損（negative PnL、n=60）を60営業日追跡した結果、「回復不能」だった
   実例は0件**。exit後60日間ずっとexit価格を下回り続けたケースは皆無だった
2. **entry価格まで回復したケース: 68.3%**（中央値6営業日で回復）
3. **反実仮想比較**: stop_lossしなかった場合（60日単純保有）と比較して、
   実際のstop_loss実行は**正味-$152,188のコスト**になっていた
   （実損失合計-$159,787 vs 反実仮想合計-$7,599）
4. 運用銘柄の年率ボラティリティは30-75%と大きく分散しており、固定-5〜-9%の
   閾値は高ボラ銘柄には1-2σ相当（統計的に「普通の値動き」）
5. 戦略自体がmax_hold_days=2〜20日の短期スイング設計であり、「数ヶ月」という
   脅威の時間軸とそもそも構造的に噛み合っていない（ポジションが数ヶ月保有
   されることがない）

stop_loss発動したが、これは市場全体のクラッシュ（SPY同日-2.6%）ではなく
半導体セクター特有の一過性ショックだった。うち5銘柄（HPE, PATH, PLTR, MDB, NOW）
はその後30-70%上昇しており、「回復不能な急落」の定義には該当しなかった。

### 方針決定: 選択肢A「役割純化」（ユーザー承認）

stop_lossの役割を「短期の損失限定戦術」に純化し、「長期資産防衛」は既存の
ポートフォリオガードレール（daily/weekly loss halt、circuit breaker、本日
実装したpromotion_gate）に委ねる方針で合意。max_hold_daysは変更しない
（数ヶ月保有前提の戦略変更は不採用と判断）。

## ATR動的閾値のヒストリカル検証（paper有効化なし、2段階）

**背景**: 「有効化しないと検証を進められないか」という質問を受け、paper環境を
汚さずにヒストリカルデータで検証する方針で進めた。

### 第1段階: 簡易検証（`scripts/simulate_volatility_adjusted_stop.py`）

過去のstop_loss発動60件を対象に、閾値調整版だったら発動していたか再計算。
- 広がった側19件中13件が実際の決済点で発動しなかったはず
- 反実仮想比較（60日盲目保有仮定）: 実損失-$28,014 vs 反実仮想+$15,702 →
  **正味-$43,716**（広い閾値の方が得だった）
- 狭まった側30件は近似計算（既発動トレードの単純比例縮小）で正味-$4,159方向

### 第2段階: 日次パス検証（`scripts/simulate_daily_path_volatility_stop.py`）

**第1段階の2つの構造的欠落を解消**するため、より厳密な検証を実施:
1. exit優先順位（trailing_stop→breakeven_stop→stop_loss→time_based）を
   無視していた問題 → `SimpleExitV2Strategy`の実メソッドをそのまま流用して解消
2. stop_loss発動済み60件のみ対象で、新規誤発動リスク（狭めた閾値が健全な
   トレードを壊すか）が検証できていなかった問題 → 全closed trade 228件を対象化

**実装内容**:
- `config/strategy/simple_exit_v2.yaml`の本番設定値をそのままハードコード
  （`PROD_CONFIG`）し、`SimpleExitV2Strategy`の`_resolve_trailing_rule()` /
  `_resolve_breakeven_floor()` / `_effective_min_hold_days()` /
  `compute_volatility_multiplier()`を呼び出して優先順位付き日次判定を再現
- 同日決済20件は日次終値ベースでは原理的に再現不可能なため除外（208件を検証）
- ATR%はエントリー時点で1回計算し保有期間中固定（毎run再計算する本番とは異なる近似）
- universe平均はエントリー日±3日窓の他トレードのATR%で近似

**検証結果**:
- サニティチェック: baseline再現のexit_reasonが実本番結果と**59%一致**
  （日中値・ブローカー約定・run時点ATR再計算の違いにより完全一致は不要な基準）
- **最重要**: 狭めた閾値による新規誤発動 = **0件**
  （前回検証できなかった最大のリスクが実質的に解消されたことを確認）
- 全体集計（195件、同日決済除く）:
  ```
  ベースライン合計PnL: -$189,862
  調整版合計PnL:       -$166,962
  正味差分:            +$22,900（調整版の方が良い）
  改善17件（+$28,597） / 悪化10件（-$5,697） / 変化なし168件
  ```
- 象徴例: NBIS(2026-06-04) stop_loss -$3,415 → 閾値が広がりtrailing_stopまで
  生存 → +$4,594（黒字転換）。PLTR(07-15)も同様のパターン
- 実行は2回再現し、完全に同一の決定論的結果であることを確認済み

**テスト**: 13件追加（`test_simulate_daily_path_volatility_stop.py`、
`replay_exit()`の優先順位・tiered min_hold・conviction tier分岐を全てカバー）。
テスト作成中に5件のテスト設計ミスを発見・修正（スクリプト自体のバグではなく、
テストヘルパーが`volatility_adjusted_stop_enabled`を明示的に有効化していな
かった等のテスト側の誤り）。

**結論**: 日次パス検証により、①優先順位を無視した粗い近似ではなく実コード
に忠実な再現、②新規誤発動リスクの直接確認、の両方が得られ、
「ATR動的閾値は正味プラスに働く可能性が高い」という結論の確度が大きく
向上した。ただし依然としてエントリー時点ATR固定・universe近似・日次終値のみ
という制約は残るため、paper実測による最終確認は引き続き必要。

**テストサマリー（本節）**: 新規13件、フルスイート1714 passed / 2 skipped
（既存無関係の2件のみ）
