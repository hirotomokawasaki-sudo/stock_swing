### 結論
**現行 max_hold_days=20 は妥当。変更不要と判断。**
根拠:
1. 発動率わずか4.4%＝足かせになっていない
2. 発動時のPF 2.44・勝率70%と良好（trailingが取りこぼした強モメンタムを正しく捕捉）

4. 2026-05-21の9日→20日延長判断（「trailingがあるのでmax_holdの役割は限定的」）が
   実データで裏付けられた
5. 2026-08-14 R3-v2-Stop-Redesignでも別の理由（短期スイング設計との整合性）で
   「max_hold_daysは変更しない」方針が既に確認済み

## 監査cron偽陽性バグの修正（`stock_swing_daily_audit`）

### 発見の経緯
「本日対応可能な改善」を探す過程で、`stock_swing_daily_audit`cron（毎日06:00 JST）が
**08月に入ってから毎日、`exit code 1`（warning）+「tracker integrity issues 9〜20件」**
を報告し続けていることに気付いた。ただし同じcron内の別スクリプト
（`build_broker_tracker_reconciliation.py`、相対%閾値使用）は同じデータに対して
毎回「0 issues」と報告しており、2つのスクリプトの判定が食い違っていた。

### 根本原因
`scripts/audit_trades_with_market_data.py`の`analyze_tracker_integrity()`が
tracker/broker間の加重平均コストの差分を**絶対$0.01**の閾値で判定していた。
株価が$10を超えると、加重平均コスト計算の丸め誤差（0.04%〜0.22%程度）だけで
簡単に$0.01を超えてしまい、実質的にほぼ全ての多ロットポジションが
「mismatch」として誤検知されていた。
実例（2026-08-15時点の実データ）:
- ANET: 差額$0.11（0.06%）→ 誤検知
- AVGO: 差額$0.93（0.22%）→ 誤検知
- ASML: 差額$0.75（0.04%）→ 誤検知

### 修正内容（`scripts/audit_trades_with_market_data.py`）
- 絶対$0.01閾値 → 相対5%閾値（`PRICE_DIFF_THRESHOLD_PCT = 0.05`）に変更
- 併存する`build_broker_tracker_reconciliation.py`のWARN閾値（5%）と統一
- 実データで検証: 修正前は20件の偽陽性mismatch、修正後は**0件**（qty/price全て一致確認）
- 実際に閾値超過するケース（コーポレートアクション見逃し等、価格が数十%動くケース）は
  引き続き正しく検知されることを新規テストで確認

### テスト
- 新規回帰テスト2件追加（`test_analyze_tracker_integrity_ignores_sub_pct_cost_basis_rounding`、
  `test_analyze_tracker_integrity_still_flags_real_price_mismatch`）
- 既存3件 + 新規2件 = 5件 all pass
- フルスイート: 1842 passed / 2 skipped（既知の無関係スキップのみ、回帰なし）
- 実運用スクリプトを`--recent-days 3`で実行し、exit code 0（クリーン）を確認
  （修正前は同じデータでexit code 1）

### 影響
- 次回06:00 JST の`stock_swing_daily_audit`から、この偽陽性ノイズが解消される見込み
- 実害はなかった（実際のqty/price整合性は常に正しかった）が、
  「今日も謎の20件warning」という無意味なノイズを排除し、本当の異常が
  埋もれるリスクを下げた
