## 追加対応: HTTP console health 不安定化の暫定修正

### 背景
- 14:21 JST の追加点検で、HTTP console は process / port ともに存在するが `/health` が timeout する状態を確認。
- `logs/launchd_watchdog.log` でも、HTTP unhealthy による再起動が 13:51, 13:56, 14:01, 14:02, 14:03, 14:08, 14:14, 14:21, 14:22 JST に発生していた。

### 原因
- `console/app.py` が `HTTPServer` で起動しており、単一スレッド処理だった。
- 重い API リクエストや詰まった接続が1本あると、軽量な `/health` まで待たされ、watchdog が unhealthy と判定する。

### 実施内容
- `console/app.py` を `ThreadingHTTPServer` に変更。
- `server.daemon_threads = True` を設定し、ハンドラースレッドが shutdown を阻害しないようにした。

### 確認結果
- `venv/bin/python -m py_compile console/app.py console/services/benchmark_service.py`
  - OK
- `venv/bin/python -m pytest tests/test_console_services.py::TestBenchmarkService -q`
  - 5 passed
- フォアグラウンド起動では `/health` が即時応答することを確認。

### 残課題
- WebSocket は実体プロセスが port 3334 で稼働しているが pidfile が stale のため、`manage.sh restart` は WebSocket 起動確認で exit 1 になる。
- HTTP 起動は launchd watchdog 経由の通常運用に戻す必要がある。

## 追加対応: WebSocket pidfile stale / restart 失敗の整理

### 背景
- WebSocket 実体は `venv/bin/python websocket_server.py` として port 3334 で稼働していた。
- しかし `.run/console_ws.pid` が消えており、`manage.sh status` は `pidfile missing/stale` と表示。
- `manage.sh restart` は pidfile が無い WebSocket 実体を止められず、再起動時に `Port 3334 is already in use` で失敗していた。

### 実施内容
- `console/manage.sh` に WebSocket pidfile 採用ロジックを追加。
  - port 3334 の listener が1つだけ存在する
  - その process command が `websocket_server.py` を含む
  - 上記を満たす場合、既存 pid を `.run/console_ws.pid` に書き戻す
- `restart_ws()` / `stop` / `restart` が、pidfile 欠落時でも既存 WebSocket 実体を採用してから停止できるように変更。
- `restart` は `restart_ws` → `restart_http` の順に整理。

### 確認結果
- `./console/manage.sh start`
  - WebSocket pidfile 欠落状態から既存 pid を採用し、status が `running` に復帰。
- `./console/manage.sh restart`
  - WebSocket 側の `Port 3334 is already in use` エラーは解消し、コマンド自体は exit 0。
- launchd watchdog 経由で HTTP / WebSocket ともに復旧。
- `./console/manage.sh status && ./console/manage.sh health`
  - HTTP console: running
  - WebSocket server: running
  - HTTP health check passed
  - WebSocket listener detected

### 補足
- この実行環境から `manage.sh restart` で直接起動した `nohup` 子プロセスは短時間で消えたが、launchd watchdog が正規常駐経路として再起動し、最終状態は正常。
