# R15: intraday対応バックテストエンジン構築・初回検証（2026-08-27）

## 背景

2026-08-26〜27にかけてユーザーから「既存バックテスト（R11-B〜R14）は全て日足
OHLCのみで行っており、本番（1日4回cron・5分足intraday二段階判定）との粒度の
不一致が戦略検討に影響していないか」との指摘。R15として5分足データを実ブローカー
APIから取得済み（`data/r15_intraday_5min_cache/`、69銘柄・2年分）に続き、
本節でこのデータを使った実際のバックテストエンジンを構築・初回検証した。

## 本番メカニズムの実装確認（コード読解）

`paper_demo.py`（1225-1306行目付近）と`IntradayMomentumFeature`を実読し、
以下の実際のメカニズムを確認した:

1. 日足パスでbreakoutシグナルを生成（既存と同じ）
2. **候補のみ**、直近5分足100本を取得（cron実行時点まで、当日分）
3. `IntradayMomentumFeature.compute()`でsmoothed_momentum（5本移動平均の
   前後比較）とVWAP乖離シグナルを計算
4. `smoothed_momentum > 0.3%` かつ `vwap_signal != 'below_vwap'` なら
   **signal_strengthを1.2倍（上限1.0）にブースト**、strategy_idに
   `_intraday_enhanced`サフィックス付与
5. 条件を満たさない場合は**シグナルをブロックしない**（ブーストするだけで、
   拒否は一切しない）
6. **exit判定には一切関与しない**（intraday結果はbreakoutシグナルの強化のみに
   使われ、`SimpleExitV2Strategy`には渡されない）

## 実装

新規`scripts/r15_intraday_backtest_engine.py`。v4エンジン（t+1約定・PIT
universe・conservative exit・slippage・portfolio cap）をベースに、日足
シグナル発生日の実際の5分足データ（R15で取得済みキャッシュ）を用いて上記の
ブースト判定を再現するレイヤーを追加。

**サニティチェック**: `use_intraday_boost=False`で実行した結果が、v4本家の
baseline（n=633, WR=0.7125, PF=1.9251, net=$107,375.5）と**完全一致**する
ことを確認——エンジンの実装が正確であることを担保。

## 結果

| | daily_only（従来手法） | intraday_aware（本番相当） |
|---|---|---|
| n | 633 | 633 |
| win_rate | 71.25% | 71.72% |
| profit_factor | 1.9251 | **1.9410**（+0.83%） |
| net_pnl | $107,375.50 | **$108,648.41**（+1.19%） |

**ブースト統計**: 626件の候補中267件（42.7%）が実際にブーストされた
（smoothed_momentum>0.3%かつVWAP割れでない）。

## 結論

**intraday boost機能の効果は既存の日足のみのバックテストが示すPF/net_pnlを
大きく歪めるものではなく、方向性は正（わずかに改善）**。効果の大きさは
+0.83%（PF）・+1.19%（net_pnl）と小さく、これまでR11-B〜R14で測定してきた
数値は、intraday機能を欠いていたとしても大枠の結論（エッジの有無、各候補の
優劣）を覆すほどの誤差ではなかったと判断できる。

これは08-26に発見した「1銘柄1ポジション排他制御によるタイミングシフト
アーティファクト」（R11-C）とは異なる種類の懸念だったが、実測の結果
**intraday粒度の欠如自体は、これまでの検証結果の信頼性を大きく損なう要因では
なかった**ことが確認できた（※下記追記で一部訂正あり）。

## 追記（同日、重要な訂正）: 排他制御アーティファクトとの交差検証

08-26にR11-C（RSI逆張り）で発見した「1銘柄1ポジション排他制御が戦略効果と
混同される」アンチパターンが、本節（intraday boost）にも影響していないかを
横展開確認した。当初の検証（上記）はv4エンジン（排他制御あり）でのみ実施
しており、排他制御なしエンジンでの再確認を行っていなかった。

新規`scripts/r15_intraday_no_exclusivity_check.py`
（`r11c_rsi_no_symbol_exclusivity.py`の排他制御なしエンジン構造 +
intraday boostロジックを合成、重複実装なし）で再測定した結果:

| | 排他制御あり（v4、当初検証） | 排他制御なし（本追記） |
|---|---|---|
| PF変化 | 1.9251→1.9410（**+0.83%**） | 2.1246→2.1177（**-0.32%**） |
| net_pnl変化 | $107,375.50→$108,648.41（**+1.19%**） | $457,198.42→$456,559.73（**-0.14%**） |
| n（取引数） | 633（両方） | 2,348（両方） |
| boost率 | 42.7%（267/626候補） | 36.8%（848/2,305候補） |

**重大な訂正**: 排他制御を除去すると、intraday boostの効果は**正から負に
反転**する（すなわちわずかにPFを悪化させる）。したがって当初の結論
「intraday boost効果は小さいが方向性は正」は、**排他制御あり条件下でのみ
成立する結果であり、本番相当（排他制御なし）条件下では支持されない**。

一方で、両条件とも効果の絶対値は極めて小さい（|ΔPF| < 1%）。これは
「効果が反転するほど脆弱で、intraday boost機構自体が戦略の優劣を左右する
ほどの影響力を持たない」ことも同時に示している——R11-Cのように「見かけの
改善が丸ごと消える」ケースとは異なり、そもそも当初から小さかった効果が
測定ノイズの範囲内で符号を変えた、という解釈がより正確。

**改訂結論**: intraday boost機構（現行実装）はPF/net_pnlに対して
**実質的に中立**（効果の大きさが測定誤差と見分けがつかない）と結論を
改める。以前の「わずかに正」という結論は撤回する。R11-B〜R14の既存
バックテストがintraday機能を欠いていたことによる歪みは、方向・大きさ
いずれの意味でも無視できる水準にあるという大枠の結論自体は変わらない。

テストスイート: `pytest -k "r15 or intraday"` 18 passed（regressionなし、
既存研究スクリプトと同様に本node系はread-only研究専用のためユニット
テスト対象外）。

詳細データ: `no_exclusivity_results.json`

## この検証の限界（正直な開示）

1. **exitタイミングの精度は未検証**: 本検証はentry側のシグナル強化のみを
   再現しており、「本番は日中複数回exit判定するが、バックテストは日足1回」
   という非対称性そのものは依然未解消。stop_loss/trailing_stopが実際に
   何営業日で約定するかの精度は、この検証の範囲外
2. **VWAP近似**: R15キャッシュはOHLCVのみを保存しており、Alpacaが返す実際の
   `vw`（出来高加重平均価格）フィールドは含まれていない。本検証では
   `(high+low+close)/3`で近似した。VWAP乖離判定の閾値（±0.5%）付近で
   境界事例の判定が変わる可能性はあるが、5分足の典型的な値幅を踏まえると
   影響は限定的と考える
3. **cron実行タイミングの近似**: 本番は「cron実行時点まで」の5分足を使うが
   （premarket/open/middayの3時点、close時点は新規entryなし）、本検証は
   「その日全体」の5分足を使用（時系列的にはシグナル確定前のデータのみを
   使う設計だが、本番の複数cronタイミングの違いは区別していない）
4. **単一の2年間・単一レジーム**: R11-B等と同じ制約を継承

## 推奨される次のアクション

1. exit側のintraday粒度対応（日中複数回のstop_loss/trailing_stop判定）は
   本検証の範囲外として残っている——影響度を見積もる価値はあるが、
   entry側ほど大きな懸念ではないと考えられる（stop/trailing自体の閾値は
   価格ベースで、日足の高値・安値で概ね捕捉できるため）
2. VWAPフィールドをR15キャッシュに追加取得し、近似誤差を解消する
   （Alpacaの5分足バーには`vw`が実際に含まれているため、再取得時に
   `vw`フィールドも保存するよう`r15_fetch_intraday_5min_history.py`を
   拡張すれば対応可能、未実施）
