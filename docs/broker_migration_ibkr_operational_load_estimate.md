# A5: IB Gateway常駐運用の日次負荷見積り（設計素案）

**作成日**: 2026-08-19
**位置づけ**: `docs/broker_migration_ibkr_plan.md` Track A-5。
現行の Alpaca 運用（ステートレスAPIキー、cronからその都度リクエスト）と比較して、
IBKR移行で新たに発生する運用負荷を見積もる。実装はTrack B。

---

## 1. 現行 Alpaca 運用との違い（前提の変化）

| 項目 | Alpaca（現行） | IBKR（移行後） |
|---|---|---|
| 認証の持続性 | APIキーは失効しない（ステートレス） | セッション/ログインが**毎日失効**する前提で設計する必要 |
| 常駐プロセス | なし（cronジョブがその都度HTTPリクエスト） | IB Gateway / Client Portal Gateway を**常時起動**しておく必要 |
| 2環境運用時のプロセス数 | 該当なし（環境変数でpaper/live URLを切替るだけ） | Paper用・Live用で**Gatewayプロセスを2つ**常駐（同一Gatewayでのpaper/live同時ログイン不可） |
| 障害時の症状 | APIリクエストがエラーを返すだけ | Gatewayが死んでいる/ログイン切れの場合、**cronジョブ自体が発注不能になる**（過去の`get_account()`メソッド不存在インシデントと同種の「静かに全BUY停止」パターンを新たに生みうる） |

## 2. 日次運用タスク（想定）

| タスク | 頻度 | 内容 | 自動化の要否 |
|---|---|---|---|
| Gateway起動確認 | 毎日（市場営業日） | IB Gateway / Client Portal Gatewayプロセスが生きているか死活監視 | 必須。既存の `broker_healthcheck.py` パターンを拡張し、Gateway疎通チェックを追加 |
| 再ログイン | 毎日 or セッション失効時 | 2FA（IBKR Mobile通知等）を伴うログインフロー | **最重要課題**。完全無人化にはIBC（IBController）のようなサードパーティツール、または2FA自動応答の仕組みが必要。人手を介する運用も選択肢（下記セクション4参照） |
| Gateway再起動 | 週次 or 日次推奨 | 長時間起動によるメモリリーク等の不安定化対策 | cron等でスケジュール再起動 + 再ログインをセットで自動化 |
| 接続断からの復旧 | 不定期（障害時） | ソケット/セッション切断検知 → 再接続 | `BrokerClientProtocol`実装（IBKRアダプタ）内でリトライ・再接続ロジックを実装（既存`RetryConfig`パターンを流用可能） |
| Paper/Live 二重運用の切替ミス防止 | 常時 | 誤って片方のGatewayに両方の注文が送られないよう、接続先を明示的にログ・監視 | `environment_id`（A3）をアダプタ層のログに必ず含める |

## 3. cron統合への影響

現行の `scripts/cron/run_paper_demo.sh` パターンは「起動→処理→終了」の
ステートレスな実行モデル。IBKR移行後は以下のいずれかの設計に変更が必要：

**案1: Gatewayを常駐デーモン化、paper_demo実行時は接続確認のみ**
- Gatewayプロセスは別途 systemd/launchd（macOS）等で常時起動管理
- `run_paper_demo.sh` 実行時は「Gatewayが起動しセッションが有効か」を確認するのみ
- Gateway死亡時はエラーを出して即座に停止（fail-closed、既存の
  guardrail hard-halt思想と一致）
- **推奨**: 既存の「fail-closedを徹底する」文化（day_start_snapshot, ledger_quality_gate等）
  と一貫性がある

**案2: cronジョブ実行のたびにGatewayを起動→処理→終了**
- 毎回ログイン（2FA）が必要になり、無人運用が事実上不可能
- **非推奨**（2FA自動化なしでは実運用に耐えない）

→ **案1を前提に設計すべき**。Gateway常駐化はTrack BのIBKR Paper接続スパイク
（`docs/broker_migration_ibkr_plan.md` D0+1週）で最初に検証する項目とする。

## 4. 2FA自動化 vs 人手運用のトレードオフ

| アプローチ | メリット | デメリット |
|---|---|---|
| IBC等のサードパーティツールで完全自動化 | 無人運用が可能、既存cronの自動化思想を維持できる | サードパーティツール依存というリスク（メンテナンス停止・IBKR側の仕様変更で壊れるリスク）。導入・検証コストが発生 |
| 毎朝の手動ログイン（人手） | 実装がシンプル、IBKR公式フローをそのまま使える | 市場開始前に必ず人が対応する必要があり、**土日明けの月曜早朝や祝日明け等のオペレーション負荷**が増える。既存のcron完全自動運用からの後退 |
| ハイブリッド（自動化を試みつつ、失敗時は人手アラート） | 現実的な折衷案 | アラート設計（既存のTelegram通知パターンを流用）が必要 |

**推奨**: ハイブリッド案。既存の `stock_swing_*_review_*` cronやTelegram通知の
仕組みが既にあるため、「Gateway再ログイン失敗 → Telegram即時アラート → 人手対応」
という既存パターンへの追加は比較的低コストで実現できる見込み。

## 5. Paper/Live 2環境運用のインフラ影響

`docs/broker_migration_ibkr_plan.md` セクション6で合意済みの「2環境運用（IBKR Paper +
IBKR Live）」を実現する場合：

- IB Gateway / Client Portal Gatewayインスタンスを**ポート番号を分けて2つ起動**
  （IBKR公式ドキュメントでpaper/live同時ログインの制約を必ず確認）
- `BrokerClientProtocol`実装（IBKRアダプタ）はどちらのポートに接続するかを
  `environment_id`に応じて切り替えられるようにする（A3の設計と接続）
- 監視・アラートもPaper用・Live用で別々に必要（既存のcron監視パターンを2セットに複製）

## 6. 見積りサマリー（暫定）

| 項目 | Alpaca（現行） | IBKR（移行後、暫定見積り） |
|---|---|---|
| 常時稼働プロセス数（ブローカー関連） | 0（cronのみ） | 2（Paper Gateway + Live Gateway） |
| 日次の人手介在ポイント | 0 | 0〜1（2FA自動化の成否次第） |
| 新規監視項目 | なし | Gateway死活監視、セッション有効性、再ログイン成否 |
| 新規失敗モード | なし | Gateway停止による静かな発注不能（fail-closed設計で緩和） |

**結論**: IBKR移行はAlpacaに比べて明確に運用負荷が増える。特に2FA自動化の可否が
プロジェクト全体のリスクを大きく左右するため、**Track B最初期（D0+1週の接続スパイク）
で最優先に検証すべき項目**として位置づける。
