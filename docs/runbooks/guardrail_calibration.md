# Guardrail 閾値キャリブレーション記録

**作成日**: 2026-07-02  
**ステータス**: hard-halt 有効（2026-07-01 以降）  
**設定ファイル**: `config/guardrails/autonomous_stop.yaml`

---

## 概要

GuardrailEngine は paper_demo の各 run で pre_trade_check / post_run_check を実行し、  
指定された条件に達した場合にポジション操作（block_buys / halt / reduce_size / ai_pause）を行う。

---

## 閾値一覧と根拠

### 1. `daily_realized_loss_pct <= -2.0%` → block_buys

| 項目 | 値 |
|---|---|
| 閾値 | -2.0% |
| アクション | 新規 buy をブロック（既存ポジションは維持） |
| 根拠 | 過去最悪日（2026-06-08: -4.35%）の約半分。日中に2%損失した場合、追加リスクを抑制する最小ライン。 |
| 誤発動リスク | 低。過去実績で -2% 以上の単日損失: 2回（06-08: -4.35%, 06-09: -2.19%） |

### 2. `daily_total_loss_pct <= -3.5%` → halt（CRITICAL）

| 項目 | 値 |
|---|---|
| 閾値 | -3.5% |
| アクション | 全 buy/sell を停止（flatten_plan なし、既存ポジションは broker で保持） |
| 根拠 | 過去最悪日 -4.35%（2026-06-08）が本ルールに引っかかる = 合理的な上限設定。3.5% は1日の最大許容損失としてリアルトレードでも妥当。 |
| 誤発動リスク | 低。warning_only 期間6日間で一度も発動なし。 |

### 3. `weekly_total_loss_pct <= -6.0%` → halt（CRITICAL）

| 項目 | 値 |
|---|---|
| 閾値 | -6.0% |
| アクション | halt |
| 根拠 | 日次 -3.5% × 2日分が余裕で収まる値。週次で資本の6%以上を失った場合はシステムに構造的な問題がある可能性が高い。 |
| 誤発動リスク | 非常に低。最悪週（06-05〜06-11）: -$74,996 / equity $1.06M ≈ -7.1%（過去ではトリガー相当） |

### 4. `broker_tracker_mismatch_count >= 1` → halt（CRITICAL）

| 項目 | 値 |
|---|---|
| 閾値 | 1件以上 |
| アクション | halt |
| 根拠 | ブローカーとトラッカーの不一致は即座に調査が必要。1件でも発生した場合は自動で停止し手動確認を促す。R1-B 以前に複数の整合性バグが発生した経験から、「ゼロトレランス」が適切と判断。 |
| 誤発動リスク | 中程度。rebuild 直後などでの一時的不一致に注意。rebuild 後はシステム再起動で解消。 |

### 5. `consecutive_losing_trades >= 5` → reduce_size

| 項目 | 値 |
|---|---|
| 閾値 | 5連敗 |
| アクション | ポジションサイズを縮小（halt ではない） |
| 根拠 | 戦略の短期パフォーマンス低下を検知する軽量指標。5連敗は統計的に有意な低下（Binomial p<0.05 at WR=50%）。halt ではなく reduce_size にすることで過剰反応を避ける。 |

### 6. `stale_price_event_count >= 3` → block_buys

| 項目 | 値 |
|---|---|
| 閾値 | 3件以上 |
| アクション | block_buys |
| 根拠 | 価格データの信頼性が低い状態での新規エントリーを防止。3件はランダムなデータ取得失敗（1-2件）と区別するための最小ライン。 |

### 7. `api_error_rate_pct >= 20%` → ai_pause

| 項目 | 値 |
|---|---|
| 閾値 | 20% |
| アクション | AI コンテキスト生成を一時停止（取引は継続） |
| 根拠 | API エラー率20%超はシステム障害の可能性。AI の判断品質が低下するリスクを回避しつつ、取引自体は機械的ルールで継続できる。 |

### 8. `order_rejection_rate_pct >= 10%` → block_buys

| 項目 | 値 |
|---|---|
| 閾値 | 10% |
| アクション | block_buys |
| 根拠 | ブローカー側の問題（margin 不足、制限超過）を早期検知するための指標。 |

### 9. `token_spend_spike_pct >= 200%` → ai_pause

| 項目 | 値 |
|---|---|
| 閾値 | 200% (2倍) |
| アクション | ai_pause |
| 根拠 | 異常なプロンプト拡張やループによるコスト暴走を防止。通常の2倍以上の消費は調査が必要。 |

## キャリブレーション期間の実績

| 期間 | 日数 | 誤発動 | 正発動すべき日 |
|---|---|---|---|
| warning_only（06-25〜07-01） | 6日 | **0件** | なし（全日損失 < -2%） |

**結論**: 閾値は適切。6日間の観察で誤発動ゼロを確認し、2026-07-01 に hard-halt を有効化。

## 過去実績での遡及評価

| 日付 | 日次損失 | トリガー判定 |
|---|---|---|
| 2026-06-08 | -4.35% | ✅ `daily_total_loss_pct` 発動 → halt |
| 2026-06-09 | -2.19% | ✅ `daily_realized_loss_pct` 発動 → block_buys |
| 他の全日 | > -2.0% | 発動なし（正常） |

06-08 は最悪日として halt が発動すべき日であり、閾値 -3.5% の設定は適切。

## 閾値変更手順

閾値を変更する場合は以下のプロセスを踏むこと:

1. `config/guardrails/autonomous_stop.yaml` を編集
2. `paper_warning_only: true` に戻して 5営業日以上 warning モードで検証
3. 誤発動が 0件であることを確認
4. `paper_warning_only: false` に変更
5. 本ファイルの「キャリブレーション期間の実績」テーブルを更新

**⚠️ リアルトレード移行後（2026-08-01〜）は閾値変更前に必ず paper 検証を実施すること。**

---

## リアルトレード移行後の考慮事項

- `daily_total_loss_pct` は realized PnL ベース。unrealized が大きく含み損になった場合は手動確認が必要。
- `broker_tracker_mismatch` の false positive: 大量注文処理中の一時的ラグは 1 run 待てば解消することが多い。
- 移行初期（08-01〜08-14）は 50% サイズのため、同じ損失金額でも pct が半分になることに注意。初期2週間は閾値を -1.75% / -3.0% に引き下げることを検討。
