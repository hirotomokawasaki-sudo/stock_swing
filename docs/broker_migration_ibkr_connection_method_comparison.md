# A4: IBKR接続方式比較 — TWS/IB Gateway vs Client Portal Web API

**作成日**: 2026-08-19
**位置づけ**: `docs/broker_migration_ibkr_plan.md` Track A-4。ユーザーが接続方式を
決定するための判断材料。**この比較は一般的に知られている両方式の特性に基づく
一次資料であり、web検索による最新情報の裏取りは今回未実施**（ツール制約）。
接続方式決定前に、IBKR公式ドキュメント（Interactive Brokers Web site の
API documentation）で最新の制約・料金・レート制限を必ず確認すること。

---

## 1. 概要

IBKRには大きく分けて2つの自動売買向けAPI方式がある：

| 方式 | 概要 |
|---|---|
| **TWS API / IB Gateway** | デスクトップアプリ（Trader Workstation または軽量版のIB Gateway）を常駐起動し、そのプロセスへソケット接続してAPIコマンドを送受信する方式。Python実装は `ib_insync`（開発終了、後継 `ib_async`）や公式 `ibapi` パッケージ経由が一般的 |
| **Client Portal Web API (CPAPI)** | IBKRが提供するREST/WebSocket型API。ゲートウェイ（Client Portal Gateway、Javaベースの軽量プロキシ）をローカルで起動し、それ経由でHTTPS呼び出しを行う。セッショントークンベースの認証 |

いずれの方式も「完全にステートレスなREST APIキー」ではなく、**何らかの常駐プロセス
（Gateway）を必要とする**点がAlpacaとの最大の違い（A1棚卸しで確認済み）。

## 2. 比較表

| 観点 | TWS API / IB Gateway (`ib_insync`/`ib_async`) | Client Portal Web API |
|---|---|---|
| **常駐プロセス** | IB Gateway（軽量版TWS）を常時起動が必要。GUIなしのheadless起動は可能だが、公式には手動ログインUIが介在する設計 | Client Portal Gateway（軽量Javaプロキシ）を起動。こちらも常駐が必要 |
| **認証方式** | IBKRアカウントのユーザー名/パスワード + 2FA（IBKR Mobile経由が一般的）。毎日の再ログインが標準（自動ログアウトあり） | セッショントークン方式。同じく2FA必須、セッションは一定時間で失効し再認証が必要（tickle等のkeep-alive呼び出しで延命は可能だが無限ではない） |
| **ヘッドレス自動化** | 公式には非対応だが、コミュニティツール（IBC = IBController等）でGUI操作を自動化し、無人再起動・再ログインを実現するのが実務上の定番。**サードパーティツール依存というリスクを許容する必要がある** | REST/WebSocketなので原理的にはスクリプトから直接ログインフローを叩けるが、2FA部分の自動化は同様に工夫が必要（IBKR Mobile通知フローがネックになりやすい） |
| **Python実装の成熟度** | `ib_insync`はコミュニティで長年使われた実績があるが**開発終了（作者引退）**。後継 `ib_async` へ移行が進んでいるがエコシステムは`ib_insync`ほど枯れていない | 公式SDKサンプル（Python含む）はあるが、コミュニティの実装例は`ib_insync`ほど豊富ではない |
| **データ構造** | `ib_insync`/`ib_async`はPythonオブジェクト（`Contract`, `Order`, `Trade`, `Fill`等）として扱いやすい高レベルAPI | REST JSON。低レベルで柔軟だが、注文/約定/ポジションの型をこちらで正規化する必要がある |
| **リアルタイムデータ配信** | ソケットのpush型ストリーミング（`ib_insync`のイベントハンドラで受信）。約定通知やポジション変化もプッシュされる | WebSocketでのストリーミングも提供されるが、ポーリング前提の設計になりがちな実装例も多い |
| **市場データ購読** | 同じくIBKRアカウントに紐づく市場データサブスクリプションが必要（paper口座でも、リアルタイムデータには有料サブスクが要ることが多い。15分遅延データは無料） | 同上（サブスクリプションはアカウント単位でAPIアクセス方式に関係なく共通） |
| **接続の安定性（実務評判）** | ソケット接続は比較的安定するが、IB Gatewayプロセス自体が長時間起動でメモリリーク等の不安定化を起こすことがあるとされ、**日次再起動が事実上のベストプラクティス** | Gatewayプロセスの安定性は同様の課題。加えてセッショントークンの失効管理が別途必要 |
| **オンプレミス/クラウド運用のしやすさ** | GUI前提の設計をheadless化する工夫（Xvfb仮想ディスプレイ等）が必要になることがある | 元々ヘッドレス志向（プロキシ起動のみ）でクラウド運用に向いているとされる |
| **ドキュメント・サポート** | 歴史が長く、フォーラム・Stack Overflow等の情報量が多い | 比較的新しいAPIで情報量はTWS APIより少なめ |

## 3. 現行システムとの相性

| 観点 | TWS API / IB Gateway | Client Portal Web API |
|---|---|---|
| `BrokerClientProtocol`（A2実装済み）との親和性 | `ib_insync`/`ib_async`のオブジェクトをRawEnvelope形式に変換するアダプタ層が必要（コールバック/イベント駆動をProtocolの同期メソッド呼び出しに変換する追加設計が要る） | REST方式なので現行`BrokerClient`（httpxベースのHTTP呼び出し）と設計思想が近く、**移植の心理的障壁は低い**可能性 |
| 既存の `httpx` 依存 | 直接は使わない（ソケット通信ライブラリが別途必要、`ib_insync`/`ib_async`が内部で処理） | `httpx`をそのまま流用できる可能性が高い |
| cron運用（既存のシェルスクリプトパターン） | IB Gatewayプロセスの起動・監視をcronとは別にプロセス管理（supervisor的な仕組み）で行う必要があり、既存の「pythonスクリプトをcronで叩く」パターンからの逸脱が大きい | Client Portal Gatewayも常駐は必要だが、シンプルなHTTPヘルスチェックで死活監視しやすく、既存cronパターンに寄せやすい |

## 4. 推奨（暫定・要ユーザー判断）

**Client Portal Web API（CPAPI）をやや推奨**する暫定意見：
- 現行`BrokerClient`実装が既にHTTP+JSON方式（httpx）であり、アダプタ設計の差分が小さい
- ヘッドレス運用・クラウド運用に寄せやすく、既存のcronベース運用パターンとの親和性が高い
- ただし、コミュニティの実装例・エコシステムの厚みはTWS APIに分がある

**TWS API / IB Gateway（`ib_async`）を選ぶ理由になりうるケース**：
- リアルタイムのポジション/約定通知をイベント駆動で受け取りたい場合
- 複雑な注文タイプ（IBKR固有のブラケット注文等）を多用する予定がある場合
- コミュニティ実装例を頼りに素早く実装したい場合

**最終判断は以下を確認してから行うべき**（本ドキュメント未検証事項）:
1. IBKR公式サイトでの両APIの最新のレート制限・機能制限比較
2. Paper口座でCPAPI/TWS APIどちらが問題なく使えるか（IBKR側の制約有無）
3. 2FA自動化の実務上の運用負荷（実際に少人数チームで無人運用している事例の有無）
4. `ib_async`（`ib_insync`後継）の現在のメンテナンス状況・Python 3.13対応状況
   （本プロジェクトは Python 3.13.10 で稼働中、`pyproject.toml` の
   `requires-python = ">=3.11"` — ライブラリの互換性を要確認）
