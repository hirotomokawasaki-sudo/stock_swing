## 4. 性能向上の実験設計

1. **現行参照を固定する。** 現行の入口/見送り/出口、実効設定・コード・ユニバース・価格版と既知の検証履歴を記録する。候補に都合のよい現行版へ差し替えない。
2. **変更は1か所に限定する。** スコア/順位、選別条件、出口/保有期間のいずれか1つ。入口と出口と数量を同時に変更しない。C11のP0・capやU較正をシグナル実験に合わせて調整しない。
3. **選定と検証を分離する。** S2で見たデータは開発/探索用。期間・銘柄・既知試行の重複を記録し、独立した未使用評価区間がなければ探索比較までとする。時系列分割境界はlabelの最大horizon・重複保有に応じたpurge/間隔を事前設定し、未来の成績が開発側へ漏れないようにする。確認的な前向き観測は候補・入力・実装・判定規則の凍結後に別IDで始める。1/3/5/10日等を診断しても、最良horizonを事後的に主評価へしない。
4. **対照と主指標を1つずつ事前固定する。** 改善比較の主指標は現行参照に対する同期間の日次費用後ポートフォリオリターン差。単純な買い方/出口、同日市場・業種、現金等は整合する窓で補助比較とする。リスク・露出・turnoverの差を併記し、単なる市場リスク増を予測力と呼ばない。
5. **運用経路を独立させる。** 対照と候補は現金/保有/ロット/予約/未決済/exitを独立管理し、未実現損益も含める。価格イベントだけの場合はPFや口座DD・年率へ昇格させない。正しい時価系列がない指標は未算出とする。
6. **費用と実装制約を含める。** 情報利用可能後の執行、売買回転・ギャップ・流動性・分割/分配・未約定・保有重複を確認。既存5bps/片道と0/2/5/10/15bps感度は仮定として表示し、実測費用と混同/二重控除しない。IBKR固有条件は確認できた範囲だけ反映する。
7. **依存と全試行を残す。** 同日・同銘柄・重複保有を独立取引と数えず、必要に応じて固定seed・4,000回以上の依存対応区間と少数局面への感度を出す。全診断区分・horizon・候補・修正履歴を記録し、複数の有意差を確証として主張するなら事前に多重性を扱う。

## 5. 入力・既存部品・作業上限

- 必要入力：全候補/順位/除外理由/no-signal、判断・feature計算・足の利用可能時刻、価格basis/feed/改訂・受信版、実効設定、当時ユニバース、初期保有/注文、entry/exit/fill/outcome。全候補がなければ約定済みの部分集団として限定し、選別効果全体を推定しない。
- **既存解の確認済み**：`scripts/r11_backtest_engine_v4.py`、`src/stock_swing/research/rolling_walk_forward.py`、`trial_registry.py`、既存decision/feature snapshot・shadowログ・comparison bookを優先再利用。日足proxyの粒度・固定notional・時点証拠の制約を、本番同等と見なさない。新しいDB/プラットフォーム/有料契約を作らない。
- 追加枠は**現行診断1仕様・1バッチ、改善候補最大1案・固定比較1バッチ**。診断で列挙した全案を利益試行しない。同じ凍結仕様の不具合修正・再現確認は履歴付きで認め、経済条件を変えたら別試行と数えて追加枠にしない。
- 旧工程の「新仮説追加0」は本依頼により**このシグナル枠のみ最大1案**へ変更。C11対Uの探索1バッチ、R14品質確認1バッチ、既存最小記録接続1経路の上限は維持し、共通部品を二重開発しない。R14の利益試行・rotation再最適化を別名で追加しない。
- 高値突破/出来高、過去のexit狭小化等の否定的結果も選定理由に含める。名称変更で再試行を隠さず、実質同じ候補を再開するなら新しい根拠・変更点を記録し、この1案枠を消費する。
- H7等の本格的な較正/ML学習・昇格の既存条件は維持。今回の診断を、その条件の通過や新しいML基盤の構築としない。

## 6. 結果の判定と適用条件

- S3で意味のある改善幅・許容するリスク/露出変化・費用前提を理由と単位付きで決める。資本選好が必要な項目だけ具体案をまとめてユーザーへ確認し、未知の値を収益結果に合わせて設定しない。
- 結果は「支持する証拠あり／支持できず／不確実／入力不適格」を区別する。探索で良かった結果を経済的合格や将来の利益保証としない。研究上の打切りは普遍的な無効性の統計的証明ではない。
- 費用後の絶対経済性、現行との差、単純な代替との差、下方リスク、偏り/欠測、独立検証の充足を別欄にする。C11対Uの不成立を補助シグナルの成績で覆さない。
- 前向き検証は本体C11対UのF1と別の研究ID・版・開始sessionで扱い、開始前に必要情報量・正式判定時点・欠測/中断条件を固定する。S4〜S6の作業レビューを繰り返しの統計的GO判定にしない。
- 本番コード/設定変更、記録ON、Paper A/B配線、BUY制限解除、注文、実弾/資本配分はこの計画追加では行わない。既存Required・G-M/G-R/G-F/G-E/G-Lと対象変更に適用される昇格条件を満たした別の具体的な適用判断とする。
