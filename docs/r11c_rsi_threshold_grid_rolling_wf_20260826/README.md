# R11-C RSI逆張り候補: 閾値グリッドサーチ + rolling walk-forward検証（2026-08-26）

**背景**: `r11c_v2_rigorous_rerun.py`で単一閾値(75.0)・単一walk-forward分割による
検証を実施し、RSI逆張りフィルタが旧結論（見送り）を覆すことを確認した。しかし
これは既存の反省事項（R13-A/Bの単一トレード依存・R11-B follow-upの単一分割点
依存）と同種のリスクをまだ抱えていたため、閾値グリッドサーチ＋rolling
walk-forwardで頑健性を追加検証した。

**事前登録した評価基準**（結果を見る前に固定、後付け選別を防止）:
- 閾値が「支持される」のは (a) 比較可能なrollの過半数でtest-window PFが
  baseline以上、かつ (b) 全期間PFがbaseline全期間PF以上、の両方を満たす場合のみ
- 75.0（R11-C原設計）を基準閾値として扱い、結果を見てから最良の値を選び直すことは
  しない

## 結果サマリー

## 重要な限界（正直に報告）

### 1. rolling walk-forwardは実質2分割のみ（4分割中2分割が比較不能）

`generate_rolling_splits(n_rolls=4)`で4つの分割を生成したが、point-in-time
universeのintro_datesが全銘柄2026年に設定されている既知の制約（R13-C item6の
`r13c_rolling_walk_forward_validation.py`と同じ根本原因）により、**test windowが
2026年より前に完全に収まる2分割（roll 0, 1）はbaseline側も候補側も取引数0件**
だった。実際に「頑健性を検証できた」のは残り2分割（roll 2: test=2026-02-12〜
06-01、roll 3: test=2026-04-29〜08-14）のみ。

初回実装では、この「両者とも0件」のケースをPFフォールバック値`-1.0 >= -1.0`で
誤って「baseline超え」とカウントしてしまうバグを自己発見・修正した（比較不能な
rollは分母・分子どちらからも除外するよう修正）。

**追加調査（本日実施）**: なぜintro_datesが全銘柄2026年なのか根本原因を確認した
ところ、`r11_symbol_universe_intro_dates.py`はgit履歴から銘柄追加日を逆算する
仕組みだが、**このリポジトリ自体のgit履歴が2026-03-27開始**（`git log --reverse`
で確認）であり、それ以前の情報は原理的に復元不可能なことが判明した。これは
コードのバグではなく、プロジェクトの記録がその日付から始まっているという
**構造的な制約**——今後rolling walk-forwardの分割数を増やしても、2026年より前を
含むtest windowが増える限り同じ問題が起き続ける。

**含意**: 「4分割中4分割でbaseline超え」という当初の（バグを含んだ）出力は
誤りで、正しくは「比較可能な2分割中2分割でbaseline超え」。サンプル数が
当初の想定より少なく、頑健性の証拠としての強度は限定的。

### 2. 閾値カーブは70付近にピークを持つ滑らかな形状（75ちょうどへの不自然なスパイクなし）

PFは閾値を60→70で単調に改善、70→85で単調に悪化する凸形状を示した。75ちょうどが
最高値ではなく70がわずかに上回っており、**「75という特定の数字を後から選んだ」
というoverfittingの兆候はない**（もし75だけ孤立して高ければ疑わしいが、
なだらかな山型カーブは「買われすぎを避ける」という基礎的なメカニズムが実際に
効いていることと整合的）。

### 3. 効果の真の内訳: 「同一銘柄のエントリータイミングシフト」であり、cap機構は一切関与していない

**自己訂正**: 当初「gross/sector/cluster capによる間接的な資金再配分効果」と
仮説したが、`enforce_caps=False`で同じ検証を実施したところPF/net_pnlが**完全に
同一**（差異ゼロ）であり、`capacity_dropped_count`もbaseline・RSI候補両方で**0**
だったことを確認した。つまりcap機構は今回の検証期間中一度も発動しておらず、
当初の仮説は誤りだった。

threshold=85（baselineから37件のみ除外）の「追加34件」を個別確認したところ、
真の原因は**エントリータイミングの後ろひでし効果**だった: v4エンジンは「1銘柄に
つき同時保有は1ポジションまで」（`if sym in open_positions or sym in
pending_entries: continue`）という排他制御を持つため、ある日のRSI逆張りフィルタが
シグナルをブロックすると、その銘柄の未使用スロットが解放され、**同一銘柄の後日の
シグナルが代わりに約定される**（例: DDOG 2026-05-11のシグナルがブロックされた
結果、別日のDDOGシグナルが新規にエントリー）。これはgross/sector/cluster cap
とは無関係の、銘柄レベルの排他制御による時間的シフト効果である。

**⚠️ 重大発見（本番コード確認済み）**: この「タイミングシフト効果」は**本番では
同様に発生しない可能性が高い**。本番の意思決定パス（`RiskValidator.validate()`、
`BreakoutMomentumStrategy.generate()`、`EntryFilterEngine.filter()`）を実際に
読んだところ、どの層にも「既存保有銘柄への新規buyをブロックする」ロジックは
存在しないことを確認した:
- `RiskValidator.validate()`は`current_positions`引数を受け取るが**一切使用
  していない**（コード内で参照すらされていない、`risk_validator.py:66-125`）
- `BreakoutMomentumStrategy.generate()`自体にも既存ポジションを参照するロジック
  はない
- `paper_demo.py`の`if o.side == "buy" and o.symbol in current_positions_full:`
  （L2365）はブロックではなく**金額上限チェックに入るだけ**で、上限以下であれば
  同一銘柄への追加buyは許可される（実際`pnl_state.json`でもLRCX/IBM等が
  `lots=2`で複数エントリーしていることを確認済み）

つまり本番はv4エンジンのような「1銘柄1ポジションまで」という厳格な制限を持たず、
既存保有銘柄への追加buyも金額上限まで許可される。したがって今回発見した改善
効果の大半（+$3,047.83のうち間接効果分）は**本番では同じ形で再現されない
可能性が高い**——本番では「同一日に同じ銘柄への重複buyが拒否されずそのまま
積み増しされる」という別の挙動になるため、このバックテストの想定と異なる。

## 結論

- 事前登録基準に照らすと、6閾値全てが形式上「supported」——ただし根拠となる
  rolling walk-forwardの実効サンプルは2分割のみで、当初期待した頑健性検証には
  未達
- 閾値カーブの滑らかな山型形状は、単一閾値75.0への疑念（overfitting）を
  一定程度払拭する
- **効果の主要因（同一銘柄エントリータイミングシフト）は本番の排他制御ルールの
  不在により、本番では再現されない可能性が高いことが本番コード確認で判明**。
  これは今回の追加検証で得られた最も重要な知見であり、R11-D判断に直接影響する

## 推奨される次のアクション

1. **本番同様のルール（1銘柄1ポジションの排他制御なし、金額上限までの積み増し
   許可）でバックテストを作り直し、RSI逆張りの直接効果のみを再測定する**——
   これが今回の発見を踏まえた最優先事項
2. point-in-time universeの制約解消（intro_datesの根本的な修正、ただしgit履歴
   自体の制約のため別の手法が必要）
3. 上記1点を経ない限り、R11-D（paper A/B昇格）への判断材料としては
   現時点の結果をそのまま使うべきではない
